# Building and releasing GisCode Core

Everything a reviewer needs to rebuild the shipped executables from a source
checkout. The build is Windows-only.

## Toolchain

| Component | Version used for the v0.1.1 candidate |
|---|---|
| Python | 3.13.15 (64-bit, from python.org; tkinter included) |
| PyInstaller | 6.22.2 |
| Runtime/build dependencies | `requirements-lock.txt` — 18 packages, every one pinned with a SHA-256 (`py -3.13 -m pip install --require-hashes --no-deps -r requirements-lock.txt`) |
| Optional build-time extra | `pyproject.toml` extras: `test`, `webview`, `yaml`, `images` |

`pyproject.toml` requires Python `>=3.13`. No other build tool, signing key or
network service is needed: the executables are produced entirely by PyInstaller.

### Why there is a lock file

`requirements.txt` states intent (`psutil>=7` plus optional extras); it does not
fix what a build installs. `requirements-lock.txt` is generated by
`packaging/make_dependency_lock.py` from the versions that actually produced the
released executables, so a rebuild cannot silently pick a different transitive
dependency. It covers the complete closure — `psutil`, `pywebview` (+`bottle`,
`proxy_tools`, `typing_extensions`), `pythonnet` (+`clr_loader`), `Pillow`,
`PyYAML`, `PyInstaller` (+`altgraph`, `packaging`, `pefile`, `pywin32-ctypes`,
`setuptools`) and `pyinstaller-hooks-contrib`.

Limitations: hashes are recorded for **Windows x64 / CPython 3.13** wheels only,
because that is the only qualified build target; Linux/macOS builds would need
their own hashes. `pip` itself is not pinned (the workflow upgrades it), and
there is no lock for the test-only extras beyond what the closure already
covers.

## Version metadata

`windows_version.py` is the single source of the PE version resource. It reads
the version from `giscode/__init__.py` (`__version__`) and the publisher and
copyright from `NOTICE`, then renders a deterministic `VSVersionInfo` script
into `build/version-resources/`. Every spec passes it as `version=`, so the
application, the acceptance build and the installer always carry the same
`ProductName`, `ProductVersion` and publisher.

## Build order

```bat
:: 1. application (one-file GUI, no console)
py -3.13 -m PyInstaller --noconfirm --clean ^
  --distpath dist --workpath build/pyinstaller GisCodeCore.spec

:: 2. acceptance build (console, hardened runtime hook)
py -3.13 -m PyInstaller --noconfirm --clean ^
  --distpath dist-acceptance --workpath build/pyinstaller-acceptance ^
  GisCodeAcceptanceHardened.spec

:: 3. installer, embedding the application built in step 1
set GISCODE_APP_EXE=%CD%\dist\GisCode.exe
py -3.13 -m PyInstaller --noconfirm --clean ^
  --distpath dist-installer --workpath build/pyinstaller-installer ^
  packaging\windows_installer\GisCodeSetup.spec
```

`GisCodeSetup.spec` stores the application as a data file, so `GisCode.exe`
inside `GisCodeSetup.exe` is byte-identical to the file from step 1. Check that
before publishing:

```bat
py -3.13 -c "from PyInstaller.archive.readers import CArchiveReader; import hashlib, pathlib; r=CArchiveReader('dist-installer/GisCodeSetup.exe'); n=next(str(n) for n in r.toc if str(n).endswith('GisCode.exe')); print(hashlib.sha256(r.extract(n)).hexdigest())"
certutil -hashfile dist\GisCode.exe SHA256
```

## Signing order

Signing is a separate, owner-controlled step (see
`packaging/signing/README.md` and `CODE_SIGNING_POLICY.md`). Because the
installer embeds the application, the order matters:

1. build the application and sign `GisCode.exe`;
2. rebuild the installer with `GISCODE_APP_EXE` pointing at the **signed**
   application;
3. sign `GisCodeSetup.exe`;
4. verify both, and confirm the embedded application hash still equals the
   signed one.

Signing a file after it is embedded would invalidate the installer, and
modifying any file after signing invalidates its signature.

## Verification

```bat
py -3.13 -m pytest -q tests
signtool verify /pa /all dist\GisCode.exe
signtool verify /pa /all dist-installer\GisCodeSetup.exe
```

## Trusted CI build

`.github/workflows/release-build.yml` builds all three executables from one
commit on a GitHub-hosted `windows-2022` runner and uploads them unsigned with a
provenance file. It runs only on manual dispatch or an owner-pushed `v*` tag —
never on pull requests — uses `permissions: contents: read`, references no
secrets, and pins every action to a full commit SHA.

The same checks run locally:

```bat
py -3.13 packaging/verify_release_artifacts.py --check-source-version
py -3.13 packaging/verify_release_artifacts.py ^
  --dist dist --acceptance dist-acceptance --installer dist-installer ^
  --provenance build/provenance.json --require-version 0.1.1
```

It fails on version disagreement, missing or wrong PE metadata, a mismatch
between the installer payload and the built application, or any code signature
(the workflow must not sign). Provenance records the commit SHA, workflow run
ID, runner image, Python and PyInstaller versions and the SHA-256 of every
artifact. Provenance is evidence, not a cryptographic attestation: it is not
signed, so verify the hashes yourself.

## Reproducibility

The build is **not** byte-for-byte reproducible: two builds from the same
extracted source at the same path produce different `GisCode.exe` bytes because
PyInstaller's `base_library.zip` is not deterministic. Archive-level comparison
of two builds shows identical entry names with every entry identical except
`base_library.zip`. Published SHA-256 values therefore identify the released
files; they cannot be regenerated from source alone. Treat the hashes as
provenance, not as a reproducibility guarantee.
